# Publishing

- Publish `@elirobinson/tokens`, `@elirobinson/react`, and `@elirobinson/ai-patterns` to GitHub Packages via Changesets. Fully automatic — no manual release step.
- **Every PR that touches a published package must include a changeset** (`pnpm changeset`). The `Quality` workflow enforces this with `changeset status --since=origin/<base>` and fails the PR if one is missing.
- On merge to `main`, `Quality` (~2m) and `Visual` (~9m) both run. `Release` (`.github/workflows/release.yml`) is triggered by **`Visual`** completing — the slower of the two — and its first step asserts, for that same commit, that the `full` sweep job concluded `success` and that a completed `Quality` run did too. Only then does it run `changeset version`, commit the bump straight to `main` as `chore(release): version packages`, publish, and push the resulting git tags — all in one job, one run, no PR to merge. If either check fails, nothing publishes, so neither a broken `main` nor a visual regression can reach the registry.
  - It has to be wired this way round: a `workflow_run` trigger listing several workflows fires when **any** of them completes, so `workflows: [Quality, Visual]` would publish on `Quality`'s completion and gate nothing.
  - The trigger is further filtered to `workflow_run.event == 'push'`, so the nightly sweep does not fire a Release against a commit that was already released. `changeset:version` would find no changesets and do nothing, so the run is pure cost.
  - The version-bump push goes out as a **dedicated release App**, not as `github-actions`. Under branch protection that push needs a ruleset bypass, and a bypass granted to `github-actions` is a bypass granted to _every_ workflow in the repo — that identity is what each one gets automatically from `GITHUB_TOKEN`. It is also deliberately a **different** App from the baseline bot (`DS_BOT_*`), whose token is exposed to pull-request-authored code during `scoped`'s Storybook and docs build; giving that identity a main bypass would let any pull request exfiltrate it and push straight to `main`.
  - Consequence worth knowing: because an App token's pushes _do_ trigger workflows, each release's `chore(release)` commit now runs `Quality` and the full `Visual` sweep, and fires one more no-op `Release` (~15 min of CI). That is the price of the version commit being verified at all — it previously carried no checks of any kind.
- `workflow_dispatch` is the escape hatch that makes the gate above reversible: if a flaky sweep blocks a publish, dispatch `Release` by hand. Keep it.
- Consumer apps need a `.npmrc` scoping `@elirobinson` to the registry, plus a PAT with `read:packages`. The token must live in the **user-level** npmrc (`pnpm config set "//npm.pkg.github.com/:_authToken" <pat>`) — pnpm 10 ignores registry credentials in a project `.npmrc`, so the `${NODE_AUTH_TOKEN}` form silently fails with a 401. In CI, `actions/setup-node` with `registry-url` generates a user-level npmrc from `NODE_AUTH_TOKEN`, which is why the release workflow authenticates correctly.
